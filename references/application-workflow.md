# 工程哲学应用工作流

仅在 `SKILL.md` 的触发门已经成立后，用于阶段评审或评审后修改的增量发布评审。它不是必须逐项填写的官僚模板；深度应与用户明确的评审阶段、修改影响和错误代价成比例。

## 1. 建立项目画布

先收集下列最小信息。缺失项标为“未知”，不要猜成事实。

| 项目 | 内容 |
|---|---|
| 目标与受益者 | 对应 V01–V02 |
| 非目标与边界 | 对应 V03–V04 |
| 硬约束与目标优先级 | 对应 V05–V06 |
| 当前事实与证据来源 | 对应 K01 |
| 高影响假设 | 对应 K02 |
| 生命周期与运行环境 | 对应 L01、V07 |
| 失败后果与风险承受能力 | 对应 E09、F11 |
| 复杂性来源 | 组件、状态、规模、组织、安全、迁移等 |

如果目标或硬约束仍不清楚，先把它们变成决策问题；不要急于画架构。

## 2. 确定评审深度

先说明触发依据、评审边界、预计读取的镜头与产出。用户已经明确进入具体评审阶段时，默认执行与该阶段相称的范围化评审，不再重复询问是否评审。不要仅因模型判断“项目复杂”就扩大范围。

### 阶段评审

默认读取最可能改变当前阶段决定的 3–6 个镜头。评审对象很窄时可以更少；不为满足数量制造无关镜头。

### 增量发布评审

审查最近一次有效评审基线后的修改，以及被修改重新打开的决定、风险、假设和证据。未受影响的旧结论沿用；纯机械修改只需确认影响并刷新基线，不从头扫描整个项目。

### 完整评审

用户明确要求完整评审时扫描全部 15 个镜头；对每个镜头记录“命中”“不适用”或“待确认”，防止无声遗漏。项目复杂或高风险本身不自动升级为完整评审。

### 高保证评审

用户明确要求高保证，或用户指定的评审标准本身要求时，在完整评审之外增加独立验证、需求—证据追踪、危害分析、演练和签署责任。高保证不是写更多文档，而是提高证据独立性和可追溯性。

评审完成后按 `review-baseline.md` 记录可比较基线。未获得创建持久文件的授权时，只在当前输出中给出基线，并明确说明它不能保证跨任务自动恢复。

## 3. 建立决策账本

对会实质改变结构、成本、风险或后续选择的事项使用下表：

| 字段 | 要求 |
|---|---|
| 决策 | 用完整问句表述，不写模糊主题 |
| 原则 ID | 只列直接改变该决定的 1–3 条 |
| 状态 | 待定 / 试验中 / 已决定 / 已废弃 |
| 选择 | 当前建议或决定 |
| 替代方案 | 至少保留一个可信替代项；没有时说明原因 |
| 约束与证据 | 区分事实、推断、假设和偏好 |
| 取舍 | 得到什么、牺牲什么、谁承担代价 |
| 可逆性 | 撤回方法、成本和最后可逆时点 |
| 验证 | 通过标准、方法、负责人和时间 |
| 复审触发器 | 哪个前提变化后必须重开决定 |

一个决定不要用十几个原则“投票”。原则用于暴露不同方面，最终仍需依据约束作选择。

## 4. 建立风险账本

风险必须是“触发条件导致后果”的可检验陈述，而不是“性能风险较大”之类标签。

| 字段 | 问题 |
|---|---|
| 触发条件 | 什么事件、负载、攻击或假设失效会启动它？ |
| 后果 | 对用户、资产、进度或环境造成什么影响？ |
| 预防 | 怎样降低发生概率？ |
| 检测 | 怎样知道已经发生或正在逼近？ |
| 缓解 | 发生时怎样限制故障半径？ |
| 恢复 | 怎样回到可信状态？ |
| 所有者 | 谁监测并有权行动？ |
| 残余风险 | 控制后仍留下什么，谁接受？ |

优先级同时考虑严重度、概率、暴露时间、可检测性和可恢复性。不要用一个乘法分数掩盖灾难性尾部风险。

## 5. 设计最小验证闭环

按“单位成本获得的信息量”排序验证活动：

1. 检查硬约束和现有事实；
2. 用分析、计算或静态工具排除不可能方案；
3. 用小型探针验证高影响假设；
4. 用原型验证关键交互或物理可行性；
5. 用代表性负载、数据和故障注入验证系统行为；
6. 用分阶段发布或试点验证真实环境；
7. 在运行中监测结果，并预设继续、暂停、回滚或扩大的阈值。

验证必须写通过标准。只写“做压测”“做安全检查”不构成闭环。

## 6. 解决原则冲突

当两条原则给出不同倾向时，依次处理：

1. **硬约束**：法律、物理和不可接受危害先排除不可行方案。
2. **目标优先级**：使用 V06 判断冲突时保护什么。
3. **证据质量**：使用 K 类原则降低关键不确定性。
4. **Pareto 比较**：淘汰被支配方案，公开剩余取舍。
5. **可逆性**：证据相近时优先低成本可撤回、故障半径小的方案。
6. **复审机制**：无法一次解决的冲突，设置阈值和复审触发器。

不要用“看情况”结束；至少说明要看哪个变量、临界值是什么、由谁决定。

## 7. 输出模板

### 精简版

```markdown
## 项目判断
- 目标：
- 边界与硬约束：
- 复杂性来源：

## 三个最关键决定
1. [原则 ID] 决定：选择；证据；代价；验证。

## 主要风险
- 触发 → 后果；预防 / 检测 / 恢复；所有者。

## 下一步闭环
- 动作；通过标准；失败后的处理；评审后的基线。
```

### 完整版

```markdown
## 项目画布
## 镜头扫描（命中 / 不适用 / 待确认）
## 决策账本
## 风险账本
## 验证与发布计划
## 运行、迁移与退役计划
## 评审结论与新基线
## 未决问题和复审触发器
```

## 8. 质量自检

交付前确认：

- 每个建议都连接到具体目标、约束、证据或失败模式；
- 同一原则没有以不同格言重复出现；
- 事实、推断、假设和偏好没有混写；
- 正常路径之外检查了过载、故障、恢复、迁移和退役；
- “更简单”“更安全”“更快”等比较有明确对象和测量方式；
- 高影响不可逆决定具有更强证据和独立检查；
- 每个关键风险都有检测与恢复，而不只有预防；
- 触发依据来自用户明确的评审阶段，或发布请求与评审后修改；
- 发布评审说明了比较基线、评审后差异以及哪些旧结论被重新打开；
- 完整或高保证范围来自用户明确请求或用户指定的评审标准，而不是模型自行升级；
- 完成的评审具有可比较的新基线；
- 输出给出了可执行的下一步和停止条件，没有擅自扩大授权。
