# 工程哲学检查点追踪

用于跨多次改动、多个任务或多个项目阶段保持评审连续性。它追踪“何时应该询问用户是否评审”，不是授权模型自动执行评审。

## 首次进入项目

1. 查找现有的项目计划、ADR、风险账本、发布清单或工程哲学追踪器，优先复用已有机制。
2. 若没有持久记录，先完成轻量基线扫描，再询问用户是否建立项目级追踪器。未经同意不要新建或修改追踪文件。
3. 优先使用项目已有的文档位置。没有约定时，建议 `.engineering-philosophy/checkpoints.md`；若需要跨任务自动发现，可在用户同意后向环境支持的常驻项目指令文件加入一条读取该追踪器的指针。
4. 若用户不希望写入仓库，只在当前任务状态中追踪，并明确说明任务结束后可能无法自动记住；可询问是否需要由环境支持的提醒或自动化，但不能自行创建。

## 生命周期检查点

基线扫描时提出少量有意义的检查点，不按每次提交或每次修改机械检查。常见阶段包括：

- 目标与边界冻结之前；
- 架构或关键技术路线确定之前；
- 对外接口、数据模型或安全边界冻结之前；
- 实现进入跨组件集成之前；
- 发布候选、迁移演练或生产试点之前；
- 权限开放、真实资金规则生效、不可逆迁移或现实设施操作之前；
- 首次真实反馈之后；
- 重大事故、需求变化、约束变化或退役计划开始之后。

检查点可以由日期、阶段事件、交付物、指标阈值或风险事件触发。日期不是必需；“接口冻结时”通常比任意日历日期更可靠。

## 触发但不立即执行

当检查点到达或新风险出现时：

1. 用一句话说明为什么现在触发。
2. 建议标准、完整或高保证级别，并列出将读取的镜头范围。
3. 说明评审预计产出，而不是虚构精确耗时。
4. 标出最后可负责时点：在什么动作之后评审价值会显著下降或风险不可逆。
5. 询问用户现在执行、延期到具体节点，还是在明确残余风险后跳过。

标准评审提议通常不阻塞当前可逆工作。只有当当前动作会跨过已记录的最后可负责时点，才暂停该动作等待明确决定；不要借评审之名阻塞无关工作。

## 状态机

每个评审项只处于一个状态：

`planned → due → proposed → accepted → in-progress → completed`

允许的分支：

- `proposed → deferred → due`：到达新的明确触发条件后重新提议；
- `proposed → skipped`：记录用户接受的残余风险与适用范围；
- `completed → reopened`：前提、需求、风险或环境发生实质变化。

不要在每次对话重复提醒 `deferred` 项；只有再次提醒条件满足、最后可负责时点临近或相关风险发生变化时才重新提议。

## 最小追踪字段

```markdown
# Engineering Philosophy Checkpoints

## Project state
- Scope:
- Current phase:
- Baseline scanned:
- Next planned checkpoint:
- Persistent reminder hook: none | project instruction | external reminder

## Reviews
| ID | Level | Reason | Status | Trigger / next reminder | Last responsible moment | User decision | Completed evidence |
|---|---|---|---|---|---|---|---|

## Changed assumptions
| Assumption | Previous state | Current state | Affected review IDs |
|---|---|---|---|
```

保持记录短小：写状态、触发条件和决定，不复制 15 个镜头或完整评审正文。正式评审结果可链接到 ADR、设计文档、风险账本或发布记录。

## 恢复长期项目

恢复工作时先读取追踪器，再判断：

- 当前阶段是否与记录一致；
- 是否已经越过某个未完成检查点；
- 延期项的再次提醒条件是否满足；
- 原假设、约束、风险或负责人是否发生变化；
- 下一项工作是否会跨过最后可负责时点。

若记录过期，先修正状态并说明依据，不因存在旧文件就假定它仍然正确。

## 交接要求

任务结束但项目未结束时，交接中必须明确：当前阶段、已完成评审、待确认或已延期评审、下一提醒条件、最后可负责时点和追踪器位置。没有持久追踪器时，明确告知这只是当前任务内状态，不能保证跨任务自动恢复。
