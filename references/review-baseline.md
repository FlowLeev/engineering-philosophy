# 评审基线与发布新鲜度

本文件只解决一个问题：用户要求发布新版本时，如何判断最近一次已完成工程哲学评审之后是否发生了修改。它不负责持续追踪项目阶段，也不创建未来评审提醒。

## 什么是有效评审基线

有效基线必须来自一次**已完成**的工程哲学评审，并能把当时的评审对象与当前候选进行比较。至少记录：

```markdown
## Engineering philosophy review baseline
- Review ID:
- Completed at:
- Review stage:
- Source revision or artifact digest:
- Reviewed scope:
- Excluded scope:
- Key assumptions and evidence:
- Result: passed | conditional | failed
```

优先使用不可歧义且可重现的标识：Git commit、tag、不可变制品摘要或版本化设计文档。只有工作树快照可用时，应记录明确文件集合及其摘要；单独的日期或“上次发布前”不足以可靠比较。

评审范围必须具体到可判断后续修改会影响哪些结论，例如模块、接口、数据模型、迁移、运行配置或发布候选，而不是只写“整个项目”。条件通过时，还要记录未决条件和依赖的证据。

## 到哪里查找

按以下顺序复用现有事实源：

1. 项目已有的评审记录或决策记录；
2. 发布清单、版本记录或带评审证据的 tag；
3. 用户明确指出的评审结果；
4. 当前会话内刚完成的评审输出。

不要把普通代码审查、测试通过、发布成功或一句“看过了”当成工程哲学评审基线。不要擅自新建追踪目录；需要持久化且项目没有合适位置时，先征得用户同意。

## 如何判断评审后修改

1. 选择与当前发布候选最相关且最近完成的有效基线。
2. 比较基线与候选的已提交差异，并检查暂存、未暂存以及会进入版本的新增文件；不能只比较远端 tag。
3. 忽略明确不会进入版本的构建产物、缓存和临时文件；其余可观察差异都算“有修改”。
4. 将差异映射到评审范围、关键假设和使用过的证据，用于决定增量评审深度，而不是用于决定是否触发。

通常需要较深增量评审的修改：

- 评审范围内的实现、配置、依赖或生成物发生语义变化；
- 接口、数据模型、迁移、权限、安全边界或运行方式变化；
- 关键假设、约束、工作负载或使用环境变化；
- 原评审依赖的测试、测量、分析或其他证据变化、失效或过期；
- 原评审明确列出的条件或未决项被处理。

通常只需简短确认的修改：

- 评审范围外且不改变共享假设的修改；
- 纯排版、拼写或无语义文档修正；
- 只改变构建时间、文件顺序等可证明不影响评审结论的机械结果。

这些仍满足“评审后有修改”的触发条件；区别只在评审深度。不要用修改文件数量、代码行数或提交数量代替影响判断。一行权限变化可能使安全结论失效，大规模格式化则可能只需确认结论未变。

## 三种判定结果

### 没有修改

列出比较基线、当前候选和差异证据，然后退出工程哲学 Skill。不得为了形式重新加载镜头或重做旧评审。

### 存在修改

触发增量发布评审：

1. 列出评审后差异；
2. 标出被重新打开的旧决定、风险、假设和证据；
3. 通过 `lens-index.md` 只路由受影响镜头；
4. 重跑受影响证据；
5. 形成新的发布结论和评审基线。

### 无基线或无法可靠比较

这不是“有修改”的证据，也不是“没有修改”的证据。向用户集中询问：是否把当前发布候选作为首次工程哲学评审并在完成后建立基线。用户未确认时退出本 Skill，不阻止其他已获授权的普通发布工作。

## 评审完成后

用当前评审实际覆盖的对象生成新基线，不自动扩大为整个项目。记录新 revision 或制品摘要、范围、排除项、关键假设、证据和结论。若评审后又发生将进入版本的修改，这个基线立即变旧，下一次发布请求将再次触发增量评审。
